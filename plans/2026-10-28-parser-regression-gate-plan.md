# Plan: cached OCR parser regression gate

Status: proposed; implementation and infrastructure decisions await operator approval.
Owner of approval: Rafael. Delivery: documentation only; no parser, workflow, data or infrastructure changes.

## Goal and boundary

For every extractor change, compare the base and proposed parsers against the same frozen cached OCR corpus. Require an explanation and exact approval for every changed result, with high-confidence field changes prominent. Never commit real OCR, extracted values, participant identifiers or source filenames. This gate measures parser stability, not whether unchanged output is correct or whether OCR acquisition works.

## Decisions required before implementation

The operator approves the data route and execution boundary first. This plan does not authorize uploading data, provisioning a bucket or role, changing repository protection, or running production writes.

| Decision            | Proposed direction                                                                                                 | Evidence still needed                                                                                                          |
| ------------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------ |
| Corpus eligibility  | Owner reviews the existing corpus and freezes an explicitly permitted snapshot                                     | Provenance, permitted use, retention, valid count and coverage by document type/layout                                         |
| Full-corpus storage | Reuse approved private object storage if available; otherwise propose a dedicated private S3 location for approval | Existing storage/access inventory, encryption policy, allowed readers and deletion owner                                       |
| Execution trust     | Full raw replay only after a human approves the exact code revision and its execution environment                  | Whether GitHub runners and log access are permitted to hold participant data; who grants access and reviews executable changes |
| Untrusted PRs       | Run fictional fixtures without raw data or privileged credentials; leave full-corpus coverage pending              | Agreed required-check behavior for forks and changes awaiting approval                                                         |
| Intended changes    | Review exact private diffs; publish only a safe summary and approval identity                                      | Approved private location for detailed evidence and reviewer access                                                            |
| Performance         | Start with sequential base/head execution, one document at a time                                                  | Full-run wall time, peak memory, disk and download time on the selected runner                                                 |

S3 encrypts new objects by default with SSE-S3; an existing encryption policy may require KMS. Encryption at rest does not prevent authorized runtime code from reading or printing plaintext. No key, role or bucket is selected by this plan. See [AWS encryption documentation](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingEncryption.html).

A private bucket alone does not make running arbitrary PR code against real OCR safe. Changes to parsers, dependencies, install scripts or workflows can expose data through logs or network access. Do not execute an untrusted head in `pull_request_target`; GitHub explicitly warns against that pattern in its [security guidance](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target). If the operator cannot approve raw execution in CI, full replay remains an approved private operation with a pending CI result until its evidence is available. Fictional fixtures must not be described as full-corpus coverage.

Derived non-identifying fixtures are a viable automatic-CI alternative, but replacing names and numbers can change line lengths, matching and layout behavior. Construct fictional values across all text, raw text, IDs and output fields while preserving the geometry needed by a case; inspect the whole fixture. Confirm the intended parser behavior still reproduces in the private environment before committing it. Merely hashing filenames or removing participant names is insufficient. Rebuilding the entire corpus this way requires a separate measured assessment, not an assumed equivalent dataset.

## Minimal replay design

1. **Freeze inputs.** Select exact base and head commit revisions and one immutable corpus snapshot. A private manifest lists every file, byte checksum and expected count. Reject empty, missing, extra, corrupt or incompatible entries. Do not infer the historical 21,090 count is today's expected count. Validate the actual object shape before parsing; do not turn failed reads into empty arrays.
2. **Run each revision independently.** Use sibling temporary checkouts and each revision's resolved dependencies. Run the same version of a small replay adapter against the public extraction interface on both. A compatibility failure is a failed comparison, not an empty result. Supply cached `textExtractionResult` and a throwing OCR delegate; perform no S3 document fetch, Textract call or cache creation. Disable Nx caching for this target and keep data and output outside cached paths.
3. **Exercise selection and parsing.** Include global automatic selection with all registered parser families, plus explicit transport-manifest, recycling-manifest and scale-ticket profiles to reproduce the earlier replay coverage. For scale tickets compare the base-supported layout list on both revisions and all head-supported layouts on head only, in forward and reverse order; compare their outcomes against the base profile. Record the exact ordered lists. New layouts are intentional additions requiring review; a layout unsupported by base is not silently dropped. This does not claim exhaustive coverage of accreditation-specific combinations.
4. **Normalize only representation.** Serialize object keys deterministically and dates explicitly; preserve array order and distinguish missing, undefined and null. Each revision must encode field presence in its complete result before any JSON serialization or process boundary, using explicit missing, undefined or value states; null belongs to the value state. The comparator reads this presence-preserving representation and retains those states in private diff endpoints. Test all three absence/value cases. Do not round weights, normalize extracted strings or discard low-confidence fields to obtain a clean diff. Separate extraction duration and other execution metadata from semantic output.
5. **Compare complete results.** Compare document type, layout, overall confidence, every nested field value and confidence, raw matches, low-confidence field lists, review reasons and review-required status. Include no-match, added/removed results and errors as outcomes. Fail on unexpected exceptions; known selection failures remain visible comparison outcomes and require explicit classification. Any count mismatch or unfinished profile fails the run.
6. **Classify changes.** Report layout changes, value additions/removals/changes, confidence upgrades/downgrades and review-status changes separately. Highlight any changed or removed field that had high confidence, plus changed values that remain high confidence. `high`/`low` parsed confidence is distinct from numeric OCR confidence. High-to-low is never hidden as an improvement. Every unexpected semantic delta fails, not only high-confidence deltas.

The output contract comes from `libs/shared/document-extractor/src/document-extractor.types.ts:6,32–45`; nested timestamps appear in `libs/shared/document-extractor-scale-ticket/src/scale-ticket.types.ts:22`. Selection ties retain registration order in `libs/shared/document-extractor/src/layout-registry.helpers.ts:106`, which is why selection and order belong in the replay.

## Differences and intended-change approval

Keep detailed JSON differences private. Each entry carries a private document key, extraction profile, field path, before/after state and confidence, and change category. Raw values, raw matches, original cache names, source hashes and exception text never enter committed expectations, PR comments, Actions artifacts or job logs. Safe PR output contains aggregate counts by profile/category, completion counts, outcome, and base/head revisions only.

Prefer a reviewed private expected-diff file paired with a nonsensitive PR rationale. Bind approvals to the corpus snapshot, exact base and head revisions, profile configuration and exact before/after differences. An approval file can be stored outside the code tree after the head is fixed, avoiding a circular dependency on its own commit hash. Any changed code, base, corpus or profile requires recomputation and review. Require exact set equality: an unexpected delta fails, and an unused or overly broad approval fails. Counts-only approval is insufficient.

Use ordinary PR review for the intended-change decision; do not create a signing system or approval service. The approved execution boundary must keep a head-controlled comparison script or head-edited expectation from approving itself. Run the comparator and approval check from the reviewed trusted gate revision, and keep the reviewed approval record outside the candidate's control. The operator selects the existing storage and human approval mechanism; until then this part is blocked for implementation.

## CI integration and reporting

Use one stable regression-check result for extractor changes. Determine the changed-path dependency closure from the repository's existing project definitions; verify it against imports rather than relying solely on a handwritten list. The initial trigger set includes:

- All `libs/shared/document-extractor*/**` and `libs/shared/text-extractor/**` files.
- CLI replay code, parser registration and their imported shared parsing dependencies.
- Relevant manifests, `pnpm-lock.yaml`, TypeScript/Nx configuration and setup actions.
- The regression workflow, corpus metadata and expected-diff approval mechanism.

Run the lightweight dispatcher for every PR update so a required result is not left absent by a workflow-level path filter. Irrelevant changes receive an explicit not-applicable result; extractor changes with no authorized full replay remain pending or fail with an actionable reason, never success. Re-run for a changed base before merge acceptance. Preserve the current deployment workflow; the new check does not acquire deploy permissions. Repository protection changes require the operator's approval.

Publish the safe aggregate summary through the job summary and check result, with explicit corpus completeness, base/head revisions and the count of approved and unexpected changes. Use existing CI surfaces instead of adding a comment bot. Detailed evidence remains in the operator-approved private location, with retention and access matching the corpus; links must not embed signed credentials or identifiers. Do not upload raw artifacts even on failure. Error reporting must use fixed safe codes; unexpected error details stay private.

## Implementation sequence and acceptance

1. **Resolve data and infrastructure choices.** Establish permission, snapshot validity and actual coverage; measure compressed size and a sequential full-run baseline. Record measured units and runner details. Set timeout and disk requirements from those results. No runtime, cost or CI timeout is asserted by this plan.
2. **Implement the headless adapter and comparator.** Reuse the extraction API and registrations above. Add fictional tests for nested values, arrays, dates, confidence, no-match, errors and input completeness. Run the CLI project's existing lint, typecheck and bounded test targets. Do not alter production parsers to accommodate the harness.
3. **Prove detection end to end.** Base versus itself on the frozen corpus must finish all profiles with zero semantic changes. Introduce a controlled fictional field/confidence/layout mutation: the actual gate must fail. Missing/corrupt files, partial output, an OCR attempt and a stale approval must fail. An exact reviewed expected difference must pass, and an extra or unused approval must fail. Remove mutations afterward. Unit tests alone do not establish these outcomes.
4. **Wire the approved CI route.** Exercise a real extractor change, a shared-dependency change, a gate change, a docs-only change and an untrusted/fork PR. Verify safe reporting on both pass and failure, no data in caches/artifacts/logs, and approval invalidation after a new head or base. Inspect the actual job result before calling the gate operational.
5. **Enable required enforcement after evidence.** Operator approves the observed runtime and data handling, then the required check. If any decision remains unresolved, keep the delivery marked incomplete and name its owner; do not substitute a skipped job for coverage.
